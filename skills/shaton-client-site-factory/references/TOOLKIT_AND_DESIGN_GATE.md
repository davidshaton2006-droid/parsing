# TOOLKIT_AND_DESIGN_GATE.md — обязательные источники и 5 макетов ДО КОДА

> **Статус: обязательный регламент для КАЖДОГО нового клиентского сайта.** Читать сразу после SKILL.md и перед WORKFLOW.md. Применяется к демо для потенциального клиента и к полноценным сайтам. Не заменяет исследования бизнеса, проверку фактов, права на материалы, UX, безопасность и QA.

## 1. Строгий порядок работы с запретом пропуска

```text
ЧИТАЕМ SKILL + TOOLKIT + WORKFLOW
       ↓
ИССЛЕДУЕМ БИЗНЕС И ПОДТВЕРЖДАЕМ ФАКТЫ
       ↓
ИЗУЧАЕМ ВСЕ ОБЯЗАТЕЛЬНЫЕ ИСТОЧНИКИ, ВЫБИРАЕМ КОМПОНЕНТЫ
       ↓
ДЕЛАЕМ РОВНО 5 РАЗНЫХ ВИЗУАЛЬНЫХ КОНЦЕПТОВ ИЗОБРАЖЕНИЯМИ
       ↓
В КАЖДОМ: ПК-ЭКРАН + МОБИЛЬНЫЙ ЭКРАН ОДНОГО ДИЗАЙНА
       ↓
ПОКАЗЫВАЕМ 5 ВАРИАНТОВ, ПОЛУЧАЕМ ВЫБОР / ПРАВКИ / УТВЕРЖДЕНИЕ
       ↓
ТОЛЬКО ТЕПЕРЬ: КОД, КОМПОНЕНТЫ, АНИМАЦИИ, ИНТЕРАКТИВНОСТЬ
       ↓
ТЕСТЫ, ПУБЛИКАЦИЯ В ОДНОМ parsing, РЕАЛЬНАЯ ПРОВЕРКА URL
```

**STOP / DESIGN GATE:** запрещено писать реализацию, запускать деплой, создавать «черновой сайт» в React/HTML, подменять пять изображений кодом, ссылками на референсы, текстовыми описаниями или одним длинным коллажем до прямого согласования одного варианта пользователем. Можно исследовать факты, референсы и компоненты, готовить бриф и изображения. Если пользователь требует начать код сразу, но ещё не утвердил один из пяти, сначала исполнить обязательный визуальный этап; если выбор отсутствует — предъявить пять вариантов и остановиться на согласовании. Если пользователь отдельно и явно отменит этот этап для конкретной задачи, уточнить приоритет с пользователем, поскольку это меняет установленный им регламент.

### Требования к каждому из 5 изображений
- Ровно **пять отличающихся вариантов** (#1–#5), каждый как **отдельная полноценная картинка PNG/JPEG/WebP**, а не один общий лист из пяти. Дизайн-борд каждого варианта включает **две проработанные версии: desktop (например 1440 px) и mobile (например 390 px)** на одной картинке. При необходимости можно приложить дополнительные close-up, но пять основных обязательны.
- На каждом варианте изображены **одни и те же реальные данные и фирменные цвета** клиента: логотип/название, основные услуги, первичный CTA, фото организации, ключевые преимущества, реальные адреса и контакты. Не выдумывать цифры, отзывы, сертификаты, цены и результаты.
- Видно не только hero, но и достаточно нижних секций, чтобы оценить композицию: категории, реальные проекты/галерея, блок доверия/конверсии, контакты (сообразно нише).
- **Сильная визуальная дифференциация:** различаются композиционная система, плотность, типографика, фото-кадрирование, ритм, глубина, тип интерактивности и структура. Пять перекрашенных копий запрещены.
- Профессионально и актуально: хорошие скругления там, где они сочетаются с брендом, выразительная сетка, премиальная типографика, фотографическая режиссура, современная адаптация; без нейрослопа, шаблонных кричащих лозунгов, бесцельных бегущих строк и декоративного прогресс-бара.
- До генерации проверить разрешённые фото/видео. Если утверждено «только материалы организации», **использовать только их**; при отсутствии доступа не подменять чужим автоспотом/нейростоком, сообщить о блокере.
- Под каждым вариантом дать краткую (1–3 предложения) особенность, ожидаемую пользу, мотивацию выбора и возможную анимацию/компонент.
- Нумерация сохраняется при обсуждении. Утверждённый №N фиксируется явно в проектном брифе и остаётся эталоном для реализации. Перед кодом можно внести согласованные замечания и повторно показать скорректированный вариант.
- **Код должен быть верен выбранному изображению**, включая пропорции, сетку, стили, размер/кадрирование фото, mobile-поведение, скругления, поля, акценты, иерархию. Сверять итоговые скриншоты с исходным изображением; не делать самовольный шестой вариант в процессе разработки.

## 2. ЧЕТЫРЕ НОВЫХ ОБЯЗАТЕЛЬНЫХ ИНСТРУМЕНТА/ИСТОЧНИКА (для каждого нового сайта)

1. **Claude Code Templates** — https://github.com/davila7/claude-code-templates
   Каталог для Claude Code: агенты, skills, commands, hooks, MCP, настройки, шаблоны. До макетов найти подходящие элементы для исследований, frontend design, UX, QA, performance и разработки; выбрать и задокументировать, что действительно подходит. При доступной CLI-среде сверить команду с текущим README. Примеры из официальной документации:
   `npx claude-code-templates@latest --search "frontend design"`
   `npx claude-code-templates@latest --skill creative-design/frontend-design`
   **Не ставить всё подряд**, не запускать непроверенные hooks/MCP или скрипты с секретами. В среде, отличной от Claude Code, изучить применимые инструкции без притворства, что шаблон уже установлен.

2. **Aceternity UI через 21st / CLI** — исходный запрос пользователя: `npx @21st-dev/cli add @aceternity`.
   Указанный аргумент `@aceternity` сам по себе **не является конкретным компонентом**: сперва выбрать полный идентификатор `@aceternity/<component>` / `aceternity/<slug>` по фактическому каталогу и текущим правилам 21st.dev. Современная документированная установка Aceternity через shadcn registry:
   `npx shadcn@latest add @aceternity/<component-name>`
   21st CLI для конкретного компонента:
   `npx @21st-dev/cli add aceternity/<component-slug>`
   Проверить имя компонента и правильный формат перед выполнением команды. Для проекта обязательно рассмотреть **реальный уместный компонент**: photo carousel, compare, motion gallery, floating dock, reveal или другое под задачу. Не использовать декоративный компонент, если он ухудшает UX, accessibility или скорость. Не выдавать перенос идеи за прямую установку.

3. **Hossain Jahed на 21st.dev** — https://21st.dev/@jahed
   Авторские компоненты/паттерны: cinematic landing hero, glassmorphism trust hero, spotlight card, limelight navigation, modern mobile menu, liquid glass button, image swiper, hero with video и другие (набор динамически меняется). Изучить актуальные превью и код при разработке пяти концептов. Определить, какие паттерны действительно полезны для конкретного бизнеса, и применить выбранный компонент либо собственную аккуратную адаптацию с соблюдением лицензии. Не копировать всё подряд и не маскировать неработающий компонент под действующий.

4. **21st.dev** — https://21st.dev/
   Обязательный поиск релевантных актуальных UI-компонентов, themes, templates и patterns по нише, нужным сценариям и стилю каждого сайта. Для React/shadcn-совместимой среды применять 21st CLI/MCP или исходники согласно документации; проверить версии, dependencies, accessibility и лицензию. Минимум просмотреть альтернативы для hero, navigation, gallery, cards, forms и мобильного UX. Записать компоненты-кандидаты для всех пяти изображений, затем реализовать только те, что соответствуют утверждённому направлению.

**Исполнение считается полноценным только при фактическом просмотре всех четырёх источников на каждый новый сайт, фиксации конкретных использованных идей/элементов и применении уместных компонентов в утверждённом дизайне.** Если конкретная CLI команда или установка технически недоступна — честно отметить блокер; не выдумывать успех установки. Нельзя называть обязательную работу выполненной, если библиотеки просто перечислены в отчёте. Пакеты — только после оценки безопасности, лицензий, bundle size, поддержки и совместимости.

### Ранее обязательные источники — СОХРАНЯЮТСЯ
- https://github.com/jakubkrehel/skills — интерфейс, типографика, цвета, композиция, UI review и доступность.
- https://github.com/nextlevelbuilder/ui-ux-pro-max-skill — дизайн-система, паттерны ниши, проверки UX и визуального качества.
- https://github.com/meta/astryx — при совместимой React 19+/StyleX архитектуре использовать подходящие компоненты; в иных стеках учитывать применимые принципы, не добавлять несовместимую зависимость.
- https://motion.dev/docs — анимации, reduced motion, performance, graceful fallbacks, Motion for JS/React.

Эти ВОСЕМЬ источников должны быть проверены перед каждым сайтом. Нет права утверждать, что они «использованы», если ссылки не открывались. Не подключать одновременно несовместимые UI-стэки ради формальности.

## 3. ОТЧЁТ О ВЫБОРЕ КОМПОНЕНТОВ — обязательный артефакт

Для каждого проекта зафиксировать:
- Ссылки и дату проверки каждого из 8 источников.
- Какие templates/skills/компоненты просмотрены, с URL конкретных страниц и почему выбран/отклонён каждый.
- Какие решения отражены в макетах №1–№5; отдельно какие попадут в утверждённый вариант.
- Если используется CLI: точная команда, версия, результат, добавленные зависимости; нельзя скрывать отсутствие доступа или выдумывать установку.
- Учитываемые ограничения: права на фотографии, производительность, клавиатура, touch, адаптивность, reduced motion, телефоны/формы/карты, известные данные организации.
- Утверждение: «вариант №N», выбранные элементы и конкретные правки пользователя.

## 4. Критерии прохождения этапов

**Gate 1 — Research:** факт-лист бизнеса, конкуренты, ЦА, референсы, фотографии/видео, сценарии конверсии, актуальность.
**Gate 2 — Toolkit:** ВСЕ 8 источников просмотрены, есть ссылки/выбор компонентов, известны ограничения лицензий и стека.
**Gate 3 — Five images:** выдано 5 ВИЗУАЛЬНО РАЗНЫХ изображений, в каждом одновременно PC + mobile, с реальным контентом/брендом и разъяснениями. Это результат, который пользователь может оценить без запуска кода.
**Gate 4 — Approval:** пользователь выбирает №1–№5 и утверждает визуал; решение зафиксировано. Без него НЕТ начала разработки или деплоя.
**Gate 5 — Build:** реализованы компоненты, контент и анимации выбранного макета; сайт не превращён в шаблон.
**Gate 6 — QA:** desktop/mobile screenshot сравнение с макетом, все интерактивные элементы реально работают, контент виден при сбое JS, факты подтверждены, скорость и доступность проверены.
**Gate 7 — Publish:** сайт добавлен отдельным `<slug>` в единственный `davidshaton2006-droid/parsing`, Actions зелёный, публичная ссылка проверена.

**Нельзя компенсировать пропуск визуального утверждения количеством кода, а отсутствие функций — красивой картинкой.**
