# WORKFLOW.md — обязательная последовательность для каждого нового сайта

1. Прочитать ../SKILL.md и DEPLOYMENT.md, затем PROJECT_HISTORY.md.
2. Уточнить текущую задачу, не переспрашивая уже известное.
3. Проверить доступность репозитория github.com/davidshaton2006-droid/parsing, права на запись, текущую ветку, существующие slug, статус Pages.
4. Открыть текущие версии всех 4 внешних источников из SKILL.md и определить, какие конкретные разделы полезны для этого проекта. Если источник недоступен — обозначить; не утверждать о применении.
5. Сохранить исходные проекты и пользовательские данные; изменения — минимально необходимые и проверенные.

## Шаг 1. Исследование бизнеса и клиента
Собери и проверь: точное имя/бренд, адрес, контакты, часы, профиль услуг, сегмент/географию, фирменные цвета/логотип, фотографии с правами использования, язык клиента, существующий сайт и соцсети, карточки на картах, внешние отзывы с датами/ссылками и атрибуцией, конкурентов в радиусе предложения, типовые боли и мотиваторы покупки.
Источник информации указывай для каждого важного факта. Учитывай, что карта или поисковый результат могут быть устаревшими. Не приписывай компании услуги/оборудование/цены/награды на основании типичности ниши.

Минимальный research brief:
- Название, ниша, город, адрес, проверенные контакты.
- Кто клиент бизнеса, что ему важно, три основных задачи/страха.
- Основная конверсия: запись, звонок, маршрут, расчёт или консультация.
- Что действительно отличает компанию от конкурентов, что — гипотеза.
- Какие данные подтверждены, что пометить «демо», что нельзя показывать как факт.
- Три релевантных ориентира конкурентов и что у них можно улучшить, **без копирования дизайна**.

При B2B-продаже сайта руководителю: выявить недостатки текущего пути клиента, показать в демо гипотезу улучшения, предложить деликатный контакт с ЛПР. При общении с администратором раскрыть и его пользу: понятные ответы на частые вопросы, меньше повторяющихся звонков, удобнее запись/маршрутизация. Не утверждать, что экономия или конверсия уже измерены.

## Шаг 2. Создать индивидуальный визуальный стиль
1. Определи визуальное направление отдельно под клиента, а не под привычки разработчика.
2. Проверь, что оно подходит для локального рынка, ниши и уровня позиционирования.
3. Сформируй токены: цвета ролей (background/surface/ink/accent/border/focus), типографика, container, spacing scale, breakpoints, elevation, радиусы, motion tokens.
4. Убедись в хорошей читаемости, контрасте и CTA на всех устройствах.
5. Применяй по назначению better-typography, better-colors, better-layout, better-accessibility и UI UX Pro Max; Astryx — только при реальном React 19+ проекте.
6. Подготовь различающиеся композиции блоков: большие изображения, асимметрия где уместна, видимые отступы, человеческие тексты; минимум визуального шума.

## Шаг 3. Контент и фотоматериалы
- Заголовки должны говорить о клиентской пользе, а не о пустой «премиальности».
- Избегай воды, шаблонных фраз, длинных тире, надуманных УТП.
- Сильный первый экран: что за компания, чем полезна, город, один понятный primary CTA.
- Подтверждённые отзывы давай со ссылкой на оригинал и без вымышленных авторов; динамические показатели можно не дублировать, если нет поддержки актуальности.
- Не подменяй реальные фото нейросетевыми без маркировки. Не вставляй водяные знаки, чужие защищённые фото или чужую фирменную айдентику без прав.
- Не выдумывай «акция заканчивается», «10000+ клиентов», «официальный партнёр», гарантии и результаты.
- Для демо-цен показывай явную маркировку «примерные цены» и не вводи посетителя в заблуждение.
- Оптимизируй изображения: размеры, современный формат, responsive sizing, loading=lazy ниже первого экрана, alt.

## Шаг 4. UX и функциональность
- Меню, mobile-nav, скролл к разделам, кнопки CTA.
- Список услуг с понятными задачами, не бесконечный каталог.
- Запись: выбрано дело, имя/контакт при необходимости, дата/время только если есть честное подтверждение. При отсутствии сервера — сценарий «подготовить сообщение», которое отправляет сам пользователь; сайт не регистрирует и не подтверждает запись. Не собирай данные в никуда.
- Доступная форма: labels, required, type, валидность, сообщения об ошибках и понятная обратная связь.
- Диалог: Escape, focus, aria-modal, restore focus, прокрутка. По возможности не делай сложный модал, если достаточно нативной формы.
- Карта/маршрут по настоящему адресу и телефону с корректными href.
- Достоверное обозначение статуса «демонстрационный концепт», особенно рядом с неподтверждёнными фактами.
- SEO: title/description/canonical (если подтверждён адрес), Open Graph, h1 один, heading hierarchy, структурированные данные только когда сведения подтверждены.
- Cookie/аналитика/ПД — только при фактическом сборе с соблюдением применимых требований; не подключать внешние трекеры без необходимости.

## Шаг 5. Motion и progressive enhancement
- Приоритет: Motion.dev; vanilla JS => Motion for JavaScript; React => Motion for React. Проверять актуальное API перед кодированием.
- Анимации должны помогать восприятию: hero entrance, мягкий stagger текста/карточек, hover/focus feedback, плавное раскрытие деталей, контролируемый scroll reveal.
- CSS-класс .reveal не должен стартовать с opacity:0 без безопасного условия. Разрешено прятать элементы только после успешной инициализации скрипта, при немедленном корректном показе; желательно вообще не скрывать контент до взаимодействия.
- На prefers-reduced-motion: reduce убрать/упростить переходы и избегать параллакса.
- Не анимировать огромные фоновые изображения, дорогостоящие blur/filter на скролле и layout свойства без нужды.
- Проверить поведение при отключённом JS, медленной сети, блокированном CDN, отсутствии внешних библиотек.
